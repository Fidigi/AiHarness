# Security and Trust Boundaries

> **Navigation:** See [`project-map.md`](../project-map.md) for repository boundaries and Docker validation.

## Overview

Security spans canonical workspace resolution, explicit project trust, HTTP/WebSocket authorization, secret storage, executable packages/extensions, MCP file inspection, explicit bounded connection testing, persistent session hosting and explicit encrypted MCP OAuth, confirmation-gated atomic import/replacement—including a serialized fresh-project trust-plus-first-write transaction—and local mutation, and safe browser rendering. Every external path, ID, credential, package source, provider response, and extension payload is untrusted.

Review [`server-api.md`](./server-api.md) for route guards and [`extensions.md`](./extensions.md) before changing executable-code loading.

## Authentication and Capabilities

| Identity | Capabilities |
|---|---|
| Anonymous when auth is configured | None; protected `/api` requests return 401 |
| User token/session | `chat`, `sessions`, `workspace:read`, `files:read` |
| Admin token/session | User capabilities plus workspace/file writes, terminal, configuration, credentials and packages |
| No configured tokens | Local requests receive admin capabilities; bind policy still applies |

`AI_HARNESS_AUTH_TOKEN` identifies a user when a distinct admin token is configured. `AI_HARNESS_ADMIN_TOKEN` identifies an admin and falls back to the user token when omitted, so a lone auth token has admin capabilities. Browser login exchanges a token for a random in-memory `aih_session` cookie with `HttpOnly`, `SameSite=Strict`, expiry, and `Secure` on HTTPS. The Settings compatibility path may instead keep an explicitly entered Bearer token in per-tab `sessionStorage`.

Origin checks cover mutations and WebSocket upgrades. Browser WebSockets use cookie auth or an encoded bearer subprotocol; any query string is rejected, the bearer protocol is never reflected, and only `aih.v1` may be negotiated.

## Workspace Boundary

```text
browser/CLI path
  -> WorkspaceManager.resolve (tilde, absolute path, realpath, allowed root, kind)
  -> inspectProjectTrustResources(canonical cwd), metadata only
  -> ProjectTrustManager.getStatus / resolveProjectTrust
  -> operation-specific capability and resolved trust check
  -> file/Git/command/agent/PTY work
```

Trust is a shared canonical-path decision map in `trust.json`; it is not a project marker such as `.ai-harness/trusted`. CLI, RPC and package-only startup locate that file through `resolvePreTrustAgentDirectory()`, never through a project-controlled `AI_HARNESS_AGENT_DIR`: the selected directory must be outside the canonical workspace with no symbolic-link component, otherwise Core chooses an independent XDG/home/UID-temporary fallback or fails closed. Only the Server composition root may mark its administrator-owned data directory `agentDirTrusted`. Each exact path may store an allow or refusal, and the nearest ancestor decision applies to descendants. Thus an exact child refusal overrides a parent allow, while an exact child allow overrides a parent refusal. Resolution order is process override, nearest saved decision, no protected resources, global `defaultProjectTrust`, then an interactive prompt or fail-closed fallback. `--approve`/`--no-approve` and session-only prompt choices never persist. Symlinks may not escape allowed roots. Never pass a browser-supplied path directly to `fs`, Git, a shell, PTY, package installer, or AgentRuntime.

Read-only workspace browsing still requires `workspace:read`; each result is capped at 500 entries and reports truncation. Direct-child creation requires `workspace:write`, rejects separators/traversal/control names and resolves both parent and future child against allowed roots. Dangerous writes/execution additionally require admin capabilities and, where applicable, resolved project trust. In the CLI, the same Core tools are rooted at the startup cwd: `read`, `grep`, `find`, and `ls` remain read-only, while `bash`, direct `!`/`!!`, `edit`, and `write` require the current canonical workspace to resolve trusted. In the CLI, a folder with no protected resource resolves true for operations in that process without persisting a decision, but its separate project-body gate remains false so a resource that appears after inventory is not opened through a check/load race; reload re-inspects metadata before loading newly appeared resources. The Web treats first workspace use and agent execution themselves as protected capabilities, so an empty folder still needs an explicit saved allow. Its status route keeps Core’s resource-sensitive `requiresTrust`/`trusted` result and reports the distinct saved-capability result as `operationTrusted`, while both use the same canonical nearest-decision store. The MCP first-import flow may create that saved exact allow only after a separate explicit fresh-folder confirmation and only inside Core’s serialized trust-plus-write transaction; resource-sensitive `trusted: true` alone never authorizes it. Core process execution shared by CLI, RPC and Web filters API keys, access keys, tokens, secrets, authorization/cookie/password/credential-like parent environment names before spawning children; do not bypass it with raw `spawn` for agent- or user-controlled commands. Cancellation terminates the process group on POSIX and the process tree through `taskkill` on Windows, then escalates after a grace period.

Instruction text is executable only in the model-policy sense, but it is still untrusted input sent to a provider. Core separates user-owned files under `AI_HARNESS_AGENT_DIR` or `~/.ai-harness` from project sources. Before trust, it may inspect only bounded `lstat` metadata for `.ai-harness` settings/resource/system paths, project skill/prompt directories, and the selected ancestor context filenames; it never reads their bodies. Interactive `ask` prompts only if this inventory is non-empty, whereas print/JSON/RPC `ask` refuses safely. Ancestor context files and `<cwd>/.ai-harness/{SYSTEM,APPEND_SYSTEM}.md` are opened only after resolved trust. Explicit CLI text-or-file flags are an intentional user read, while Web configuration values are always literal and cannot turn into arbitrary server file reads. Every discovered file must be a nonsymlink regular UTF-8 file and is subject to per-file, file-count and aggregate limits plus an open/stat identity check. Resolved disk contents are ephemeral provider options and are not copied into session metadata. Do not move project body discovery before the trust check or expose resolved bodies through capabilities/catalogue APIs.

Agent settings use the same source boundary: an agent-directory `settings.json` is user-controlled only when that directory is independently trusted; an override located in the workspace is treated as project-controlled and cannot supply settings, trust, credentials, themes, prompts, instructions or executable resources before trust. Project `.ai-harness/settings.json` is likewise not opened until canonical project trust. Project `sessionDir`, extensions, resources, credential commands, models, proxies and tool settings all remain behind that boundary. Reads default to 256 KiB (the injectable hard ceiling is 1 MiB), reject symbolic-link path components, hardlinks, non-files, invalid UTF-8/JSON, NULs, and identity/timestamp races, and use a parent-directory descriptor on Linux. Validation keeps valid fields while omitting unknown or invalid values, and diagnostics never include setting values. `/settings` intentionally omits proxy values, credential commands and opaque telemetry identifiers.

The MCP Settings reader follows a narrow file-only contract. Core may read `<data-dir>/mcp.json`, but it opens `<cwd>/.ai-harness/mcp.json` only when the nearest persisted trust decision is `true`; implicit resource-sensitive trust for an empty folder is not enough. Before that it uses `lstat` metadata only, so a file that appears after an empty-folder check is still not opened. Both files must be regular and nonsymlink, are capped at 1 MiB, and pass open/stat race checks, JSON/JSONC syntax, depth 64, server-count 200 and strict shallow entry validation. Parse errors are fixed text that never quote source. API descriptors omit env/header values, identify command-backed fields and variable names without resolving them, escape hidden characters, and redact executable paths, literal arguments, URL credentials/path/query/hash. Opaque revisions are keyed per process so they detect stale bytes without becoming a browser-visible hash oracle for low-entropy literals.

MCP paste preview is a separate non-mutating Core contract. The browser sends the original text, an explicit `foreign` or `aiharness` syntax choice and optional cwd; an edit preview additionally identifies one existing scope/name/revision, but it never sends a normalized object for the server to trust. Core reparses at most 256 KiB, 20 servers, 128 fields, depth 64, 128 collection items, 256 shell words and 16 KiB per string/word. Its shell lexer treats commands as data and refuses operators, redirections, substitutions, multiple commands and evaluator forms such as `sh -c`, `cmd /c` and `pwsh -Command`. It accepts a bounded subset of direct commands, client add commands, JSON/JSONC shapes and Cursor/VS Code/Visual Studio/Copilot install links, drops unknown keys with typed counts, and refuses SSE, WebSocket and unsupported schemes.

Foreign `$...` and initial `!` literals are escaped before any future persistence shape is described; explicit variable forms in supported shell/client commands remain references, while only an AiHarness-syntax choice or recognized `ai-harness mcp add` command recognizes native command-backed fields. References are permitted only in env values, header values and `oauth.clientSecret`, never URL/command/arguments. Server supplies only `Object.keys(process.env)`, never environment values. The public preview contains structural field names, masked targets, variable names and fixed diagnostics, but no normalized raw configuration, literal secret, argument text, header/env/OAuth value or source excerpt. Literal secrets make project scope ineligible; remote available-variable references require explicit confirmation; `AI_HARNESS_AUTH_TOKEN`, `AI_HARNESS_ADMIN_TOKEN` and `AI_HARNESS_MASTER_KEY` references make every scope ineligible. Project collision/trust decisions come from a fresh redacted inventory, so project file content is still never opened without an effective persisted allow. A decision-free folder with no trust-requiring resource is project-eligible only when the bounded breadth check excludes filesystem/home/data roots, other known folders and unprotected nested projects; its fail-closed scan inspects at most 256 paths and 2,000 directories through depth four, rejecting links, special types, read/identity races and exceeded depth. A nested subtree with its own nearest decision is already protected and does not inherit the candidate allow. Preview then reports a `fresh-project-trust` confirmation rather than granting trust. Preview does not write files, resolve a value, run a process, contact a URL, initialize OAuth or open/create a credential store.

Import and replacement persistence do not trust the preview or a browser-built object. The browser resends the original paste plus one entry index, target scope/name, bounded missing-field values or variable names, literal-secret approval and exact remote host-variable approvals. Replacement also supplies the exact existing target name and its inventory revision; current hidden values are never loaded into the form. Core reparses the original text, applies only fields it independently rediscovered, escapes literal completion in reference-capable locations, and rechecks schema, shell/management commands, unsupported/reserved references, final secret locations and confirmations. A project write refuses every remaining literal secret; a global write with remaining literals requires explicit approval; an available host variable referenced by a remote header or OAuth secret requires name-bound approval. The write then uses the same opaque revision, trust checks, lock, no-follow reread and atomic file replacement as other mutations. A confirmed `trustProject: true` is accepted only for a project import with a missing target revision. Core serializes it on the trust-store lock, rechecks canonical folder identity, direct/ancestor trust resources, nearest allow/refusal and bounded breadth, persists one exact allow, acquires the MCP lock, revalidates again, then writes. A failed write removes only that exact newly introduced decision; a failed rollback carries typed `trustKept` state, and every failure causes canonical inventory and workspace trust reload. A replacement changes or renames exactly one valid entry, removes omitted fields, preserves siblings, and refuses collisions. Neither success nor failure returns the normalized/written entry, old values, source literals or host values.

Local MCP insertion, whole-entry replacement, activation, exposure changes, removal and restoration retain the same no-resolution boundary. The administrator route passes original import text plus bounded choices, or local mutation selectors, together with an opaque revision to Core; Core serializes cooperating processes with a bounded owner-only heartbeat lock, rereads under that lock, rejects stale/malformed/linked/nonregular files, and writes a same-mode same-directory temporary file before fsync and atomic rename. One request inserts or replaces exactly one selected entry, changes at most 100 unique activation selectors, or changes one valid entry/default or exact remote-name `toolExposure` override to `direct`, `codemode`, `deferred` or `hidden`, and publishes at most one file replacement. Exposure is configuration metadata only: selecting it never loads tools or opens a transport, and choosing the server-wide `direct` default removes the optional property. Hidden tools are neither declared, discoverable nor nested-callable; wholly hidden servers are not started for prompts unless a non-hidden override makes them eligible. Explicit Test can still contact a hidden entry. Global writes force `0600`; project writes retain existing permission bits or use `0644` for a new file. Accepted JSONC is normalized to JSON with the first bounded indentation style, original LF/CRLF style and one final newline while unknown keys survive. Project trust is checked before any directory/body access, again inside the lock and immediately before commit.

Removal literals, including possible secrets, remain only in a server-memory FIFO of at most 100 records and expire through unreferenced 60-second timers. The browser gets only a random token and ISO expiry. Restoration consumes that token, compares the deletion revision, rejects name conflicts and rechecks project trust; neither failures nor API responses serialize the held entry.

The explicit MCP **Test** is the sole exception to configuration administration’s no-resolution rule. The browser sends only `{ scope, name, cwd? }`; Core rereads and validates the entry from its file, requires a fresh persisted allow before any project body and again for a configured project cwd, and the Server resolves every cwd through `WorkspaceManager`. Core refuses reserved server credential references, starts stdio with `filteredProcessEnvironment()` or contacts the configured Streamable HTTP URL, serializes tests that use command-backed values, joins identical in-flight tests, and bounds shell resolution, each MCP request, the whole test, pages/items, stderr/errors and closure. Success, failure, timeout and shutdown all close the transport; a stuck stdio child is signaled after the close grace. An HTTP authorization challenge becomes `needs-auth` without starting OAuth or opening a credential store. Results redact configured and resolved env/header values plus sensitive OAuth/command/argument/URL parts before returning bounded server identity, cwd, counts and tool summaries. OAuth client secrets are not resolved because Test never starts OAuth. Status is volatile and shown only for the exact scope/source/name/config key; an observed edit removes stale status. Test never invokes a tool or grants trust, and a Configured row still does not mean Connected.

Persistent MCP hosting is a separate Core boundary, not an extension of the administration routes. `AgentRuntime`, the CLI loop and RPC ask `McpSessionHost` to reread inventory and each target only immediately before a prompt. Project files and configured project working directories require the same fresh persisted allow as Test; a process-only trust override is insufficient. A second config-key comparison closes the inventory/target race. Disabled, removed, shadowed or changed records are closed, and changed same-name records close before replacement. Per session, at most 32 servers are retained, each server contributes at most 500 bounded-schema tools, and at most 1,000 tools enter one prepared declaration/discovery snapshot. Direct connections alone delay a prompt, within the 20-second connection deadline; codemode/deferred connections never publish direct declarations or delay it. An explicit `tool_search` can then wait abortably for their already bounded connection attempt. Command-backed connections take a serialized host slot. Connections are reused only while the exact config key/cwd remains current, retry after failure/disconnect on the next prompt, consume tool-list-change notifications, close after the explicit post-prompt idle window and participate in bounded process shutdown.

MCP OAuth is an explicit active boundary separate from inventory and Test. The exact `GET /api/mcp` path bypasses credential initialization; listing therefore opens no encrypted store. OAuth status/start/poll/paste/cancel/logout require the administrator `configuration` capability and no-store responses. Status re-resolves only submitted scope/name/config-key descriptors and returns booleans without an URL or credential. Start rechecks canonical cwd, persisted trust and the exact target, then Core joins or allocates a random-ID detached flow capped at 32 active/100 retained records, five minutes active and one minute retained. It binds only `127.0.0.1` on `/oauth/callback`, validates callback or pasted URL origin/path/state/code, bounds remote transport and redirects, and uses the MCP SDK for protected-resource/issuer discovery, PKCE, configured clients or dynamic registration and token exchange. Only phase, stable failure code, authorization URL and loopback callback URL reach Web; tokens, refresh tokens, client secrets and verifiers do not.

Every OAuth credential write rereads the target and trust, compares scope/name/source/config key/cwd/normalized URL and refuses disabled or changed entries. A post-login MCP connection is independently opened with a passive provider before success. Configured `!command` client secrets run only after an OAuth challenge or explicit sign-in and join the live redactor immediately. Initial connections serialize command-backed resolution in the host; explicit flows serialize per credential identity. There is no process-wide command slot shared by Test, detached flows and later passive refresh. Encrypted records use opaque SHA-256 name-plus-normalized-URL store keys, bounded schema parsing and atomic exact-value replacement. Logout increments a process-local generation before lock-serialized credential removal, so providers created earlier cannot save refreshed tokens afterward. A non-secret random revocation marker remains encrypted to reject even an empty-baseline cross-process writer; random document revisions and provider-local CAS snapshots prevent ABA and status-read resurrection. It also aborts the identity's active flow and closes matching process-local host connections. No issuer revocation request is currently made.

Ordinary CLI, RPC and Server/Web MCP hosts all use Core's same passive provider factory. They may use or refresh existing state after a challenge but `redirectToAuthorization` fails as `needs-auth`: only explicit Web sign-in or top-level CLI `mcp login` can publish an authorization URL. Missing `AI_HARNESS_MASTER_KEY` leaves OAuth endpoints stably unavailable rather than falling back to plaintext. The shared OAuth fetch wrapper bounds headers and finite response bodies for explicit discovery/exchange and passive refresh, including challenges during tool calls. Only the exact MCP GET notification stream retains its connection lifetime; OAuth responses claiming an event-stream content type still time out. Closing a connection aborts its outstanding fetches. Cancellation aborts discovery/exchange/verification and closes the callback listener immediately, even if an asynchronous driver ignores abort; shutdown is bounded.

A direct or discovered MCP tool call is unattended model-directed execution. Provider-safe names are deterministic and collision-hashed, but a name is not authorization: the prepared session binding, current declaration, active allowlist and connection are checked again at invocation. A `read-only` run exposes only tools whose server declared `annotations.readOnlyHint: true`; missing hints are treated as unsafe, including after a tool-list notification. The same extension before-tool hooks/events wrap static, search and MCP execution. Inputs must be bounded JSON objects, MCP requests carry cancellation/deadlines, binary payloads are omitted, text/structured output is bounded, and configured/resolved env/header/URL/argument credentials are redacted before model, session, CLI/RPC event or Web rendering. Chat labels MCP calls as server/tool; Settings reports volatile connecting/connected/needs-auth/failed/disconnected/closed state without values.

`tool_search` is capability selection, not authorization. Core bounds query/document/schema/candidate/result counts, searches only codemode/deferred tools that already passed preset/allowlist/exclusion/extension and MCP read-only policy, and records only host-authenticated matches. Only deferred matches become direct declarations; codemode matches remain script-only. Definitions are recomputed atomically before the next provider call; the fixed declaration set for the current response rejects a candidate called alongside its search. Persisted activation names follow only their session branch and are re-filtered against current tools and policy after resume or fork, so edited metadata, a removed tool or changed exposure cannot manufacture a callable binding. Dynamic candidates remain prompt-local and never mutate `ExtensionRegistry`.

MCP servers are not a sandbox. A configured stdio server executes with the AiHarness OS identity, selected trusted cwd, filtered but still useful environment, filesystem rights and ambient network access; a remote server receives configured headers plus model-selected tool arguments. Users must treat enabling a server and choosing `direct`, `codemode` or `deferred` exposure as granting a discoverable unattended capability, prefer least-privilege server processes/containers and read-only tools, and disable entries not needed for a session. Both indirect modes are searchable, but codemode tools remain script-only. The separate [QuickJS sandbox](./codemode.md) isolates user JavaScript, not MCP servers or nested host tools: no ambient Node/files/network/timers, a disposable worker, VM/stack/fuel/deadline/input/output/call/concurrency ceilings, current eligible-tool checks before every nested operation (including queued calls), and success-only redacted branch-store publication. Hidden/model-only controls, recursive code mode and subagent controls cannot be nested. Authorized calls already made are not rolled back on failure; classifier/image execution is unsupported. OAuth does not make MCP a sandbox or add tool authorization. Ordinary HTTP connections may passively use and refresh encrypted state but never begin interactive authorization; an explicit Settings flow or CLI `mcp login` is required after `needs-auth`. Do not claim an exposure mode provides a sandbox or that the current read-only policy can make a falsely annotated third-party tool safe.

Core skill and prompt discovery loads project roots only after trust, does not traverse symbolic links, caps selection at 10,000 files, and opens each Markdown resource as a stable no-follow UTF-8 regular file with one link and a 1 MiB limit. Strict CLI, RPC and Server skills require frontmatter, `name`, `description`, and a normalized name exactly matching their directory. Settings selectors apply ordered exact/glob inclusion and exclusion to resolved paths, preserve metadata-only provenance, and retain valid collision candidates for catalogue policy. Local and package extension code still passes the extension loader's separate regular-file, hardlink, size and trust checks immediately before import. Core exposes project package paths only after the same trust decision, and package filters can only narrow resources already declared by a validated manifest. Custom and package theme files use the same bounded reader; explicit paths inside the workspace are project resources regardless of how the caller labels them.

The trust store accepts only bounded absolute paths and boolean decisions. Reads are size-capped and regular-file-only; malformed, linked or unsafe stores fail closed. Mutations re-read under a bounded heartbeat lock, merge decisions, write owner-only temporary files and rename atomically so CLI and Web processes do not silently overwrite one another. Credential, trust, plugin and session lock release first atomically claims an unpredictable sibling and revalidates device/inode before unlinking; a pathname replacement is restored rather than deleted. Fresh-folder transactions hold that same inter-process lock across their first write, so concurrent trust mutations cannot be overwritten and a rollback restores the exact prior decision map. Async status checks refresh when the file identity changes. Legacy v1 `trustedProjects` entries are read as allows and migrate to v2 on the next mutation; no project-controlled file can grant trust.

Truncated interactive CLI and direct RPC shell output is retained under an owner-only temporary directory and returned as `fullOutputPath`; the Web command adapter uses the same runtime without exposing a server-local path. Retained output expires after 24 hours by default through an unreferenced per-file timer and safe scavenger; cleanup takes a bounded stable directory enumeration, rejects truncated scans, atomically quarantines each expired candidate, and deletes it only after device/inode revalidation. Symbolic links and pathname replacements are never recursively removed. Clients may still delete files immediately after consumption, and operators should treat the temp directory as sensitive.

## Secret Storage

| Data | Persistence |
|---|---|
| Built-in provider credentials | Core `EncryptedCredentialStore` in `credentials.enc` with `AI_HARNESS_MASTER_KEY` and an independently trusted agent/data directory; environment, command and explicit CLI values may remain process-local, but login/API persistence is refused without the store |
| Custom provider secrets | The same Core store/service format in `provider-secrets.enc`; API keys and headers use separate namespaces, and a secret-bearing mutation is refused without the master-key-backed persistent store |
| Push private key/subscriptions | `push.enc` only with master key; otherwise volatile |
| MCP configuration literals | Operator-managed `mcp.json`; pasted import/replacement text and field completion remain transient request data, preview/inventory/action responses are redacted, confirmed global writes may persist literals, project writes may not, replaced values are never returned, deleted literals remain briefly in bounded server memory for undo, Test/session hosts resolve eligible values only in Core and return aggressively redacted volatile status/results, and files still need OS-level protection |
| MCP OAuth credentials | Versioned bounded documents under opaque SHA-256 name/normalized-URL keys in Core `credentials.enc`; access/refresh tokens and dynamic-client secrets require `AI_HARNESS_MASTER_KEY`, never cross to the browser, and share atomic compare-and-set plus process-local logout generations with passive CLI/RPC/Web refresh |
| Non-secret configuration | Atomic `config.json`, `providers.json`, `plugins.json`, `subagents.json` |

Core model catalogues contain descriptors only: provider/ID/name, availability/source, capabilities, limits, prices and non-secret compatibility flags. Remote discovery is timeout/retry/result bounded and validated before a descriptor reaches CLI, RPC or Web. `--api-key` constructs an in-memory provider override and must never be copied into catalogue entries, protocol descriptors or session settings; users should still prefer environment or protected secret storage because command-line arguments can be exposed by shell history and process inspection.

Never expose provider keys, OAuth tokens, server-side authorization headers, passwords, master keys, VAPID private keys, or subscriptions through API/RPC responses, diagnostics, logs, sessions, fixtures, browser storage, shell child environments, terminal replay, or command recovery. `CredentialRedactor` is a process-local, non-enumerable inventory populated at credential ingress. It covers raw, URI, base64/base64url, hex and JSON-escaped variants; bounds secrets, variants, matches, text, JSON nodes/depth and streaming-prefix state; handles cycles and hostile getters; and fails closed on oversized or opaque secret-bearing values. Every chunked channel owns an independent stream and flushes it before its terminal event, so a credential split across provider, tool, shell, extension, accidental JSON-mode stdout/stderr, SSE, WebSocket or PTY chunks is removed before persistence or emission. Legacy sessions are scrubbed and atomically rewritten after newly discovered credentials load.

The sole raw-output exception is the exact interactive local command `/credential reveal <provider>`; it is refused outside a local TTY and no broader command-result flag bypasses redaction. The explicit compatibility Bearer is a separate browser-auth exception: it may live only in per-tab `sessionStorage`, never `localStorage`, workspace caches, logs, or documentation. Session/provider serializers additionally strip broad API-key/secret/token/password/cookie/credential field variants, but callers must still avoid placing secrets in generic metadata.

`EncryptedCredentialStore` uses AES-256-GCM with `scrypt`, bounded documents/entries/values, owner-only files/directories, no-follow opens, hardlink and ownership checks, parent-component validation, heartbeat locking, exact-value compare-and-set and fsync-backed atomic replacement. Credential resolution order is environment, trusted `providerApiKeyCommands`, process memory, then encrypted storage. Command stdout is bounded and process-local. Provider OAuth refresh accepts only bounded HTTPS endpoints/responses and emits stable errors without reflecting remote text.

## Executable Extensions and Packages

- Load project code/resources and model instructions only after trust.
- Refuse symlinked extension modules and modules over 5 MiB.
- Keep GET catalogues and CLI `package list` metadata-only and side-effect free.
- Parse only supported npm, HTTPS Git, and allowed local sources; relative local paths are a CLI-only convenience resolved against its canonical cwd.
- Disable npm lifecycle scripts and use shallow Git clones in staging.
- Reject linked package roots/resources, traversal and out-of-package filters; bound state, manifest, scan depth/count and resource count.
- Serialize every CLI/Server mutation under the same heartbeat lock, refresh state inside it, and commit owner-only temporary files by atomic rename.
- Bound group activation to 100 unique entries, authorize each project enable independently, keep project disable available for cleanup, and commit all allowed changes in one state write without altering resource filters; flag untrusted cleanup for runtime reload without reopening package contents.
- Validate a complete managed candidate before atomic replacement and restore its backup if package or state publication fails.
- Exclude resource bodies, source code, command output and credentials from catalogues and diagnostics.

These controls reduce exposure; they do not sandbox trusted third-party JavaScript, which runs with the privileges of the active CLI or server OS user.

## Browser Content Security

- Render extension widgets as text and interactions from a fixed schema.
- Sanitize supported Markdown/KaTeX/Mermaid output; keep raw HTML non-executable.
- Validate uploads by count, size, name, collision policy, and canonical destination.
- Store provider credentials only server-side; bounded session caches explicitly strip key-like fields.
- Use focus traps and safe cancellation/reconnection for extension dialogs; accessibility behavior is part of the security contract.

## Network Boundary

Core routes provider HTTP and WebSocket traffic through one bounded policy: optional HTTP(S) proxy dispatchers, request/idle/connect deadlines, capped provider retry/delay, strict URL handling, abort propagation and stable errors that omit URL, body, headers and proxy credentials. Native JSON requests/responses are capped at 16 MiB with fatal UTF-8 decoding; streaming events, output and tool/content-block counts have separate limits. OpenAI Responses WebSockets use exclusive bounded cached leases, hashed session identities and bounded continuation. SSE fallback is allowed only before the first WebSocket event so an operation is never replayed after remote processing begins.

The launcher binds to `127.0.0.1` by default. A non-loopback bind without authentication is rejected unless the explicit insecure override is set. Public deployment still requires a trusted HTTPS reverse proxy or private network, correct allowed origins, and proxy-level request limits.

Opening a workspace in the host file manager is narrower than ordinary authenticated access: both the Host header and actual socket peer must be loopback, the platform must have an explicit command mapping, and the requested cwd must resolve as an allowed directory. The shared Core launcher never invokes a shell and passes only desktop/session environment keys, not API keys, auth tokens or arbitrary server variables. The availability probe and action are no-store; remote clients receive no action.

## Common Changes

### Add a capability or protected route

Update `ApiCapability`, role sets, route middleware, browser behavior, and anonymous/user/admin plus Origin tests.

### Change paths, files, commands, or PTYs

Resolve through `WorkspaceManager`, require the correct capability/trust state, bound all input/output, and test traversal, escaping symlinks, mismatched workspace IDs, and cancellation.

### Change secret persistence

Keep non-secret metadata separate, require master-key encryption for disk persistence, use atomic restrictive files, redact diagnostics, and test restart plus no-key behavior.
