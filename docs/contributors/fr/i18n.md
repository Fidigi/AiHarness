# Internationalisation de l’interface Web

L’interface Web d’AiHarness utilise une petite couche i18n interne. Elle reste dans
le package `@ai-harness/web` et n’ajoute aucune dépendance d’exécution. Les réponses
reçues des modèles, le contenu des sessions, les noms de modèles et de providers ainsi que
les erreurs détaillées renvoyées par le serveur ne sont pas modifiés.

## Langues disponibles

Les paquets de langue intégrés sont :

- `en` — English ;
- `fr` — Français.

Au premier chargement, la langue est déduite de la liste
`navigator.languages`. Les variantes régionales, par exemple `en-US`, `fr-FR` et
`fr-CA`, sont associées à leur langue intégrée. L’anglais est utilisé lorsqu’aucune
préférence du navigateur n’est prise en charge.

Le sélecteur de langue se trouve dans l’en-tête de la barre latérale. Un choix
explicite est enregistré dans `localStorage` sous la clé `ai-harness-locale` et
reste prioritaire sur la langue du navigateur lors des visites suivantes. La
balise `<html lang>` est mise à jour à chaque changement.

## Utiliser une traduction dans un composant

Les composants React obtiennent la fonction de traduction avec `useI18n` :

```tsx
import { useI18n } from '../hooks/useI18n.js';

export function ExampleButton() {
  const { t } = useI18n();

  return <button aria-label={t('example.open')}>{t('example.open')}</button>;
}
```

Le composant doit être rendu sous `I18nProvider`. Le point d’entrée
`packages/web/src/index.tsx` fournit déjà ce contexte à toute l’application.

Utilisez des paramètres pour les valeurs calculées plutôt que de concaténer des
fragments traduits :

```tsx
<p>{t('settings.totalSessions', { count: sessionCount })}</p>
```

Le message correspondant conserve la structure propre à chaque langue :

```ts
// en.ts
'settings.totalSessions': 'Total sessions: {count}'

// fr.ts
'settings.totalSessions': 'Nombre total de sessions : {count}'
```

## Ajouter une langue

### 1. Créer le fichier de messages

Ajoutez un fichier dans `packages/web/src/i18n/messages/` avec un identifiant de
style BCP 47. Pour un paquet japonais, créez par exemple
`packages/web/src/i18n/messages/ja.ts` :

```ts
import type { LocalePlugin } from '../types.js';

/** Paquet de langue japonais pour AiHarness Web. */
export const jaLocale: LocalePlugin = {
  id: 'ja',
  label: '日本語',
  messages: {
    'common.language': '言語',
    // Ajouter ici toutes les autres clés partagées.
  },
};
```

Copiez l’ensemble des clés de `messages/en.ts` avant de commencer la traduction.
L’anglais est le paquet de référence et le fallback. Une clé manquante revient à
sa valeur anglaise, puis à son propre identifiant si elle manque également en
anglais. En développement, une clé absente produit un avertissement dans la
console.

### 2. Enregistrer le paquet

Importez le paquet et ajoutez-le à `localePlugins` dans
`packages/web/src/i18n/registry.ts` :

```ts
import { jaLocale } from './messages/ja.js';

const localePlugins: readonly LocalePlugin[] = [enLocale, frLocale, jaLocale];
```

`getSupportedLocales()` l’exposera automatiquement au sélecteur. Si la langue
possède des règles de correspondance régionales particulières, adaptez aussi
`resolveBrowserLocale()` et ses tests.

### 3. Mettre à jour le type des locales

Ajoutez l’identifiant au type `Locale` dans
`packages/web/src/i18n/types.ts` :

```ts
export type Locale = 'en' | 'fr' | 'ja';
```

Cette étape maintient la vérification statique des locales intégrées et de leur
persistance.

### 4. Ajouter les tests

Complétez `packages/web/src/i18n/registry.test.ts` lorsque la détection du
navigateur ou la liste des locales change. Complétez
`packages/web/src/i18n/format.test.ts` si l’interpolation ou le fallback change.
Une nouvelle langue doit au minimum vérifier :

- son identifiant et son libellé dans le registre ;
- une traduction représentative ;
- l’égalité de ses clés et paramètres d’interpolation avec le paquet anglais ;
- les variantes de langue du navigateur qui doivent lui correspondre.

Ajoutez un parcours dans `e2e/i18n.spec.ts` lorsqu’un changement concerne le
sélecteur, la persistance ou la mise à jour visible de l’interface.

## Ajouter ou modifier un texte d’interface

1. Ajoutez une clé stable dans **tous** les paquets de
   `packages/web/src/i18n/messages/`.
2. Regroupez les clés par fonctionnalité : `chat.*`, `settings.*`, `sidebar.*`,
   `provider.*`, etc.
3. Utilisez `t('namespace.key')` pour les textes visibles, les `title`, les
   `aria-label` et les `placeholder`.
4. Utilisez l’interpolation pour les nombres, noms et autres valeurs dynamiques.
5. Ne traduisez pas les noms de produit, providers, modèles, variables
   d’environnement, chemins, commandes, contenus utilisateur, réponses du modèle
   ou détails d’erreur fournis par le serveur.
6. Ne traduisez jamais une erreur d’API en comparant son texte anglais. Traduisez
   seulement le texte local qui l’entoure.

Conservez les termes techniques établis lorsque leur traduction compliquerait le
lien avec la configuration ou la documentation : `API Key`, `Provider`, `Token`,
`SSE`, `WebSocket`, `JSONL`, noms de modèles et noms de variables d’environnement.

## Vérification

Les validations du dépôt s’exécutent dans Docker depuis la racine :

```bash
make typecheck
make test
make test-e2e
```

Le test du registre impose aux paquets intégrés le même jeu de clés et les mêmes
paramètres `{nom}` que le paquet anglais.

## Principes de conception

L’internationalisation est limitée à l’interface utilisateur et reste
incrémentale. Ajouter une langue ne doit pas modifier les contrats API, la
persistance des sessions, les sorties du modèle ou le serveur. Le registre, les
paquets de messages et le hook React constituent volontairement une couche
simple afin qu’une contribution puisse ajouter ou améliorer une traduction sans
introduire de framework supplémentaire.
