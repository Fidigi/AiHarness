# Web Interface Internationalization

AiHarness Web interface uses a small internal i18n layer. It stays within the `@ai-harness/web` package and adds no runtime dependencies. Responses received from models, session content, model and provider names as well as detailed errors returned by the server are not modified.

## Available Languages

Built-in language packs are:

- `en` — English;
- `fr` — Français.

On first load, the language is deduced from `navigator.languages`. Regional variants, for example `en-US`, `fr-FR` and `fr-CA`, are mapped to their built-in language. English is used when no browser preference is supported.

The language selector is located in the sidebar header. An explicit choice is stored in `localStorage` under key `ai-harness-locale` and takes priority over browser language on subsequent visits. The `<html lang>` tag is updated on each change.

## Using a Translation in a Component

React components obtain the translation function with `useI18n`:

```tsx
import { useI18n } from '../hooks/useI18n.js';

export function ExampleButton() {
  const { t } = useI18n();

  return <button aria-label={t('example.open')}>{t('example.open')}</button>;
}
```

The component must be rendered under `I18nProvider`. The entry point `packages/web/src/index.tsx` already provides this context to the entire application.

Use parameters for computed values instead of concatenating translated fragments:

```tsx
<p>{t('settings.totalSessions', { count: sessionCount })}</p>
```

The corresponding message preserves language-specific structure:

```ts
// en.ts
'settings.totalSessions': 'Total sessions: {count}'

// fr.ts
'settings.totalSessions': 'Nombre total de sessions : {count}'
```

## Adding a Language

### 1. Create the messages file

Add a file in `packages/web/src/i18n/messages/` with a BCP 47 style identifier. For a Japanese pack, create for example `packages/web/src/i18n/messages/ja.ts`:

```ts
import type { LocalePlugin } from '../types.js';

/** Japanese language pack for AiHarness Web. */
export const jaLocale: LocalePlugin = {
  id: 'ja',
  label: '日本語',
  messages: {
    'common.language': '言語',
    // Add all other shared keys here.
  },
};
```

Copy all keys from both `messages/en.ts` and the feature-local `components/settings-locale-en.ts` before starting translation. Keep the latter in the corresponding feature pack, add that pack to `components/settings-locale.ts`, and provide boundary loading/error/retry copy in `components/settings-locale-boundary-messages.ts`. English is the reference pack and fallback. A missing key falls back to its English value, then to its own identifier if also missing in English. In development, a missing key produces a warning in console.

### 2. Register the pack

Import the pack and add it to `localePlugins` in `packages/web/src/i18n/registry.ts`:

```ts
import { jaLocale } from './messages/ja.js';

const localePlugins: readonly LocalePlugin[] = [enLocale, frLocale, jaLocale];
```

`getSupportedLocales()` will automatically expose it to the selector. If the language has particular regional matching rules, also adapt `resolveBrowserLocale()` and its tests.

### 3. Update locale type

Add the identifier to the `Locale` type in `packages/web/src/i18n/types.ts`:

```ts
export type Locale = 'en' | 'fr' | 'ja';
```

This step maintains static checking of built-in locales and their persistence.

### 4. Add tests

Complete `packages/web/src/i18n/registry.test.ts` when browser detection or locale list changes. Complete `packages/web/src/i18n/format.test.ts` if interpolation or fallback changes. A new language must at minimum verify:

- its identifier and label in the registry;
- a representative translation;
- equality of its keys and interpolation parameters with English pack;
- browser language variants that should match it.

Add an e2e scenario in `e2e/i18n.spec.ts` when a change concerns the selector, persistence or visible interface update.

## Adding or Modifying Interface Text

1. Add a stable key in **all** corresponding eager or feature-local packs; do not duplicate a relocated key in `packages/web/src/i18n/messages/`.
2. Group keys by feature: `chat.*`, `settings.*`, `sidebar.*`, `provider.*`, etc.
3. Use `t('namespace.key')` for visible texts, `title`, `aria-label` and `placeholder`.
4. Use interpolation for numbers, names and other dynamic values.
5. Do not translate product names, providers, models, environment variables, paths, commands, user content, model responses or server-provided error details.
6. Never translate an API error by comparing its English text. Only translate the local text surrounding it.

Keep established technical terms when their translation would complicate linking with configuration or documentation: `API Key`, `Provider`, `Token`, `SSE`, `WebSocket`, `JSONL`, model names and environment variable names.

## Settings-only Copy

`components/SettingsLocaleBoundary.tsx` wraps the existing lazy Settings route. Its loader imports `settings-locale.ts` only on entry and registers both built-in feature dictionaries before mounting business controls. Shared/dynamic/default labels remain eager. `settings-locale-inventory.json` records the accepted literal relocation and consumer classification; update its conservation proof deliberately when changing these dictionaries.

`registerFeatureLocaleMessages()` fills missing strings in existing registered packages in place, preserving references and custom overrides (including empty strings). It ignores unregistered IDs and bounds each package to 512 strings, 256-character keys and 16,384-character values. The hook, formatter and existing missing-key fallback are unchanged; fallback is not the normal French loading state.

Loading and failure remain local, translated and closable. Failed imports stay rejected on reopen; the explicit **Reload and retry** button reloads the page rather than claiming the failed ESM module became ready. Navigation/unmount retires the pending view without focus, scroll or navigation effects. Closing returns to chat, where an ongoing detached run remains stoppable.

`components/settings-locale.test.ts` checks literal/consumer/placeholder conservation, fill-only bounds and loader behavior. `e2e/settings-locale-asset-load.spec.ts` uses real production assets with deliberately delayed/failed dictionary requests and controlled API fixtures; it covers locale changes, keyboard/axe, retry and obsolete close/session/workspace completion. It is not a live-provider test. Existing Settings/defaults/model/skill/i18n journeys and historical captures remain unchanged.

## Verification

Repository validations run in Docker from the root:

```bash
make typecheck
make test
make test-e2e
```

The registry test enforces eager built-in packs to have the same keys and `{name}` parameters as the English eager pack. The Settings allocation test independently verifies the exact eager-plus-feature union and feature placeholders; new languages need both sets.

## Design Principles

Internationalization is limited to the user interface and remains incremental. Adding a language must not modify API contracts, session persistence, model output or server. The registry, message packs and React hook are intentionally a simple layer so that a contribution can add or improve a translation without introducing an additional framework.
